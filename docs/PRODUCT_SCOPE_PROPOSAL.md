# P02 — 사용자·민감정보·첫 제품 범위 제안

2026-10-25. 상태: **제안 작성 완료 / 제품 선택 G1 미채택**.
현행 [보안 모델](SECURITY_MODEL.md)과 [아키텍처](ARCHITECTURE.md)를 변경하지
않는다. 기준 구현은 `3b8c9ea`의 Linux arm64 기술 MVP이며 이 제안의 새로운
보호 범위를 구현·검증한 것으로 취급하지 않는다.

## 1. 제품 정의

권고 정의: **사용자가 지정한 민감 자원에 접근한 AI 실행이 허용된 경계 안에서만
그 정보를 사용하도록, 실제 접근·전파 근거와 효과를 관찰하고 지원되는 경계에서
집행하는 도구**.

첫 사용자는 자기 개발 환경에서 AI 도구를 실행하는 개발자다. 첫 배포 단위는
Linux arm64의 통제된 실행이며 macOS 사용자는 Linux VM 안에서 실행한다.
호스트 전체 AI 활동 자동 발견, 회사 전체 DLP, 모든 원격 DB 보호를 첫 제품에
포함하지 않는다. Source→Label→Propagation→Sink→Decision은 유지한다.

자동 내용 탐지와 흐름 통제는 별도 기능이다. 사용자 지정 또는 승인된 자원
메타데이터가 민감도 지정 근거다. 문자열·PII·LLM 분류로 보안 모델을 대체하지
않으며, 지정하지 않은 자원을 안전하다고 표시하지 않는다.

## 2. 민감정보와 위험 작업의 용어

| 개념 | 의미 | 예시 / 경계 |
|---|---|---|
| 민감정보 | 허용되지 않은 열람·이용·전달이 사용자나 조직에 피해를 줄 수 있는 정보 | 개인정보, 비공개 소스/업무 데이터, 비밀키. 파일 형태에 한정되지 않음 |
| 보호 자원 | 정책이 지정한 정보의 출처 또는 대상 | 파일, DB view/조회 profile, API 결과. 첫 구현 후보는 파일 하나 |
| 분류 근거 | 자원을 왜 보호 대상으로 지정했는가 | 사용자 지정·신뢰된 자원 등록. 실제 내용 탐지 결과와 구별 |
| 접근 근거 | 무엇이 실제로 일어났는가 | 성공한 FileOpen, 시도한 open, DB 연결, 중개된 결과 전달은 각각 다른 사실 |
| credential 비밀값 | 인증에 사용하는 비밀 데이터 | API key 파일의 원문 노출 |
| 작업 권한 | 그 credential/주체로 수행할 수 있는 효과 | DB 조회·수정·삭제 권한. 비밀값을 숨겨도 과도한 작업 권한은 남음 |
| process label | 특정 프로세스에 지정 source 접근 근거가 있음을 나타내는 상태 | 현재 Go reference 의미 유지. 실제 출력 byte의 민감성 증명이 아님 |
| 실행 보호 상태 | 같은 실행 전체에 보수적 제한을 적용하기 위한 별도 상태 **제안** | 자식 접근 뒤 부모/형제 제한. 부모가 실제로 읽었다는 event를 만들지 않음 |
| sink | 제한된 정보가 넘어갈 수 있는 집행 경계 | 외부 송신, 실행 밖 IPC/파일 반출, 사용자 표시. 첫 범위에서 각각 허용/거부/미지원 명시 |
| 위험 작업 | 자원·operation·목적지·권한·접근 이력 조합으로 판단할 효과 | command 이름 자체를 위험의 정의로 사용하지 않음 |

DB 연결 event만으로 어떤 조회가 실행됐고 어떤 행을 받았는지 알 수 없다.
SSH/원격 MCP/API를 통한 조회도 보호 대상이 될 수 있지만 실제 결과 유입을
식별할 신뢰된 경계와 우회 방지가 필요하다. 이 조건 없는 일반 원격 source
보호는 미지원으로 남긴다.

## 3. 민감한 명령어는 어떻게 다룰 것인가

| 명령 예 | 구체적으로 판단할 것 | 현재 관측만으로 주장하면 안 되는 것 |
|---|---|---|
| `cat customer.csv` | 지정 파일 접근 여부, 접근 process와 실행 귀속 | 모든 파일 내용이 실제 소비됨 |
| `curl` / Python HTTP 요청 | 실제 목적지·송신 시점과 source 접근 이력 | curl 실행만으로 유출 또는 안전 판정 |
| `psql` / SDK 조회 | DB 권한·등록된 조회 범위·결과 전달 | TLS 연결만으로 SQL/행 민감도를 파악함 |
| `rm`, DB DELETE, cloud 삭제 API | 실제 unlink/쓰기/API operation의 권한 | SECRET label이 없으니 파괴 작업도 안전함 |
| `git push` | 저장소 데이터 전송 및 원격 변경 권한 | argv 사후 관찰·kill이 이미 발생한 전송을 취소함 |

접근/작업 권한 정책과 정보 흐름 정책을 구별한다. 첫 slice는 민감 source 이후
송신 제한에 집중하며 일반 파괴 명령 예방 기능을 동시에 추가하지 않는다.
도구 이름/argv는 보조 근거일 수 있지만 실제 effect와 hook 시점을 대신하지 않는다.

## 4. 첫 사용 방식 비교와 권고

| 방식 | 사용자 가치 | 추가 신뢰/구현 부담 | 이번 권고 |
|---|---|---|---|
| 로컬 AI 분석 | 민감 데이터를 외부 서비스에 보내지 않고 개발자에게 결과 제공 | 모델과 worker를 같은 통제 실행에 두고 외부 daemon/공유 cache 우회 제한 | 첫 시나리오 후보 |
| 승인 cloud AI | 기존 cloud agent workflow 유지 | 해당 데이터 범주의 외부 전송을 사용자가 허용한다는 의미. 비식별화·provider 내부 보호는 별도 | 다음 선택지 |
| 민감 작업 분리 실행 | cloud agent는 작업 지시만 하고 민감 결과는 받지 않음 | 요청/결과 중개·인증·출력 검토·경계가 추가됨 | 첫 제품에서는 보류 |

로컬 모델도 별도 외부 daemon이 데이터를 받으면 하나의 sink다. 첫 fixture에서는
모델·agent·worker를 같은 보호 실행에 포함하고 모델 파일은 실행 전 준비한다.
실제 모델 설치와 성능 확인은 P06 이후 별도 사용성 검증이며 이번 문서에서
특정 모델이나 새 다운로드를 결정하지 않는다.

## 5. 첫 정상 작업과 금지 효과

**정상 작업:** 개발자가 지정한 합성 고객 샘플 파일 하나를 로컬 AI로 분석하고
집계/오류 설명을 본인 전용 터미널에서 확인한다. 첫 시험에는 실제 고객정보나
실제 credential을 사용하지 않는다. 사용자 출력은 명시적으로 허용한 전달
경계이며, 개발자가 이후 수동 복사하는 행위까지 AgentTaint가 통제하지 않는다.

**금지 효과:** 해당 source에 접근한 뒤 같은 실행의 부모·자식·형제 프로세스가
승인되지 않은 외부 수신기로 데이터를 보내는 것. source 접근 전후에 같은
수신기를 사용하여 차이를 검사한다. 자식이 파일을 열고 부모가 송신하는 경우,
접근 전에 열린 연결로 송신하는 경우를 반드시 포함한다.

실제 제품 사용성은 로컬 AI 작업의 성공으로 확인하고, 경계의 정확성은 결정적인
작은 helper fixture로 별도 확인한다. helper 성공만으로 AI 제품 효용을 통과시키지
않으며 모델 답변 정확도를 정보 흐름 보안의 근거로 사용하지 않는다.

첫 source는 통제된 read-only fixture로 고정한다. path alias, inherited FD,
기존 mapping 등 대체 접근 경로가 없는지 격리 제공자가 증명하거나 해당 접근을
시작 전 거부해야 한다. 현재 raw path 매칭만으로 alias 보호가 된다고 주장하지 않는다.

## 6. 최소 보호 profile 제안

| 영역 | 첫 범위 후보 | 수용 전까지의 상태 |
|---|---|---|
| Source | 사용자가 지정한 파일 하나, 현재 SECRET 단일 label 재사용 | classification 자동화 없음 |
| 근거 | process별 실제 관측과 보수적 source-attempt projection 구분 | 성공 open과 byte read 혼용 금지 |
| 전파/상태 | process 근거 보존 + run 전체 sticky 보호 상태 후보 | **규범 변경 필요**, 현재 미구현 |
| Sink | 정책상 외부 송신. 선택한 profile은 기존 연결 포함 필요한 송신 경로를 gate해야 함 | 정확한 hook/기법은 P06 검증 후 선택 |
| 격리 | 검증된 외부 실행 환경이 escape/외부 IPC/공유 경로를 제한; AgentTaint는 요구 capability를 확인 | 제공자 미선정, 새 sandbox 자체 구현은 비목표 |
| 결과 | 동일 사용자에게 로컬 표시만 허용; 자동 파일 반출·다른 run 공유 없음 | 화면/감사에는 payload 기본 비수집 |
| 산출물/cache | 실행 전용 임시 영역·생애. 다음 run 재사용/내보내기는 첫 범위에서 거부 | teardown·잔존 process/FD/cache 확인 필요 |
| 원격 자원 | DB/API/SSH source 중개 없음 | P09 조건부로 유지 |

모든 송신을 실행 시작부터 막는 대조군은 격리 효용을 보여줄 수 있지만 source
접근 이력에 따른 IFC의 추가 가치를 증명하지 못한다. P06에서 source 전 정상
송신/후 금지 송신 차이를 입증하지 못하면 이 제안의 IFC slice는 실패로 기록한다.
선택한 환경이 필요한 경계를 제공하지 못하면 fallback을 조용히 켜지 않고 해당
profile launch를 거부한다.

## 7. identity·상태·권한의 기본 구분

- ProcessKey는 기존 process birth/scope identity를 유지한다. run ID는 실행
  생애 단위이고 현재 `session_id`는 POSIX session 의미다. 대화 session으로
  재해석하지 않는다. 사용자 표시용 conversation 참조가 필요하면 별도 필드로 검토한다.
- run-wide 상태 후보는 단조 증가한다. exec, 자식 종료, 로그 삭제, UI 숨김은
  제한을 해제하지 않는다. 종료·정리 완료 전 동일 run ID를 재사용하지 않는다.
- source 접근 전 상태 반영과 이후 송신 gate의 순서를 동기적으로 보장해야 한다.
  audit 소비 뒤 사후 kill로 이 순서를 대신하지 않는다. 미지원 경쟁 경로는 숨기지 않는다.
- 정책 의미·우선순위는 Go policy/taint 소유를 유지한다. 외부 엔진을 채택할 경우
  두 evaluator를 별도 권위로 병행하지 않으며 G2에서 단일 정책 권위와 변환 계약을 정한다.
- 대상 agent가 정책·제어 socket·source 등록·scope membership을 바꾸지 못해야 한다.
  동일 UID 외부 process와 공유 daemon은 격리 검증 대상이다.

## 8. G1에서 선택할 사항과 최소 규범 변경안

권고: **로컬 사용자 시나리오 + 파일 하나 + run-wide 제한 후보 + 검증된 격리
제공자와의 조합을 비교 실험**한다. DB broker는 추가하지 않는다. P06의 결과로
기존 엔진 재사용/조합/자체 구현을 선택한다. 이 권고는 채택 전 제안이다.

| 선택 | 현행 계약 | 제안하는 변경 | 반영 대상 |
|---|---|---|---|
| A. 실행 제한 단위 | process label과 fork/exec 전파 | process 사실은 그대로 두고 run-wide 집행 상태를 별도로 허용 | AGENTS Architecture Rules, SECURITY_MODEL projection, ARCHITECTURE 책임 |
| B. 송신·격리 책임 | 지원 source/open·새 IPv4 connect와 명시 한계 | 새 profile의 기존 연결/실행 밖 경계·capability·실패 의미를 명시. 외부 격리 제공자의 책임을 분리 | ARCHITECTURE, THREAT_MODEL, Phase prompt |
| C. 화면 순서 | F9는 Phase 0~8 이후 | 첫 검증 slice의 저장/조회 계약 뒤 로컬 읽기 화면을 만들 수 있도록 UI 의존성을 재검토 | ROADMAP, Phase 9 prompt, master plan |
| D. 원격 source | 현재 파일 source | 변경하지 않음; broker는 별도 G1/P09 결정 | 현재 규범 유지 |

A/B의 규범 문구 초안: “성공한 파일 접근의 process audit 의미는 유지한다.
별도로 승인한 실행 보호 profile은 source 접근 시도의 동기 projection에 따라
동일 run의 sink를 보수적으로 제한할 수 있다. 그 상태는 다른 process가 실제로
정보를 읽었다는 증거가 아니다. 지원 capability·격리·실패 수용 조건을 충족한
profile만 실행하며, 미검증 경로는 해당 보장에 포함하지 않는다.”

C는 제품 데이터·보안 계약을 먼저 검증한 뒤 읽기 전용 사용자 화면을 배치하자는
순서 변경 제안이다. Kubernetes 기능을 미리 구현하거나 이미 완료로 표시하지 않는다.
G1 확인 전 현행 규범·코드·prompt는 수정하지 않는다.

## 검증 상태

이 문서는 제품/용어/정상·금지 사례/변경안 작성 산출물이다. 새로운 profile의
Linux runtime, local model 사용성, DB 보호, run-wide/send enforcement는
`not_tested`다. byte-level taint tracking을 주장하지 않는다.
post-event detection을 prevention이라고 부르지 않는다.
